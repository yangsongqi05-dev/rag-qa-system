========== 性能优化：从零讲清楚 ==========

一、优化的基本思路
优化的第一步不是改代码，是找到慢在哪。没有定位就动手，等于蒙着眼睛调参数。
正确的顺序是：先打开慢查询日志找出慢 SQL，再用 explain 分析为什么慢，然后针对性地改；最后才是考虑加索引、改表结构、分库分表。
这条链路里，绝大多数问题在加对索引这一步就解决了。

二、慢查询日志
慢查询日志记录执行时间超过阈值的 SQL，是定位性能问题最直接的工具。
查看是否开启：show variables like 'slow_query_log';
查看阈值：show variables like 'long_query_time'; 默认是 10 秒，实际应该调到 1 秒甚至更低。

开启并设置阈值：set global slow_query_log = on; 以及 set global long_query_time = 1;
日志文件位置用 show variables like 'slow_query_log_file'; 查看。
慢查询日志里记录的每一条都是候选优化对象。因为它会记录所有超时的语句，包括那些没走索引的，所以它同时也是一份缺索引清单。

三、用 EXPLAIN 分析
找到慢 SQL 之后，第一步就是加 explain 看执行计划。
重点看三个字段：type、key、rows。
type 表示访问类型，效率从高到低依次是 system、const、eq_ref、ref、range、index、all。看到 all 就是全表扫描，必须优化。看到 index 是扫整个索引树，通常也要优化。

key 是实际用到的索引名。如果这里是 NULL，说明没走索引。possible_keys 显示理论上可用的索引，key 才是实际用的，两者不一致时通常意味着优化器选错了索引。
rows 是预估扫描行数。这个数字越接近表的实际行数，说明扫得越多。
Extra 字段里的信息很关键。出现 Using index 说明用了覆盖索引，是好消息。出现 Using filesort 说明需要额外排序。出现 Using temporary 说明用了临时表。后两者通常意味着 order by 或 group by 没有利用上索引。

四、最常见的优化手段
第一条：建索引。这是性价比最高的手段。给 where、order by、group by 用到的列建索引，优先建联合索引而不是多个单列索引。
第二条：避免索引失效。索引列上不要用函数、不要做运算、不要隐式类型转换、like 不要以通配符开头。这些在索引那一节详细讲过。

第三条：用覆盖索引避免回表。把 select 需要的列都放进联合索引，避免查到主键再回主键索引取数据的那次额外开销。
第四条：只查需要的列，别写 select 星号。它会带来三个问题：可能读了很多用不上的列、无法使用覆盖索引、网络传输量变大。
第五条：优化 limit 分页。limit 100000, 10 会先扫 100010 行再丢掉前 100000 行，越翻到后面越慢。优化办法是用上次的最大 id 做游标：where id 大于 上次最大 id order by id limit 10。这样每页都只扫 10 行，速度恒定。

第六条：多数情况用 join 代替子查询。子查询可能产生临时表，而 join 通常能利用索引。不过这条不是绝对的，要看执行计划。
第七条：批量操作。插入多条数据时用一条 insert into 表 values (...), (...), (...) 而不是循环单条插入；删除大量数据时分批删，避免长事务。

第八条：合理使用 or。or 两边都有索引时可以用索引合并，但只要有一边没有索引，整个查询就会全表扫描。这时可以改写成两次查询再 union。

五、表结构层面的优化
第一，选合适的数据类型。能用 int 就别用 varchar；能用 tinyint 就别用 int；金额用 decimal 而不是 float，因为 float 有精度问题。
第二，尽量给列加 not null 约束并设置默认值。因为 NULL 会让索引统计和聚合函数都变复杂，而且 InnoDB 里 NULL 值也要占用存储空间。

第三，单表字段不要太多。字段多会撑大行记录，一个数据页能装的行数变少，查询效率降低。
第四，大字段（text、blob）如果要频繁查询，考虑拆到单独的扩展表。因为大字段会挤占数据页空间，还会让 select 星号 变得很慢。

六、大表优化
当单表数据量到千万级，即使索引用对了，写入和查询也会变慢。这时候要考虑三条路。
一是读写分离。主库负责写，从库负责读，用 binlog 同步。适合读多写少的场景。
二是垂直拆分。按业务把一张宽表拆成几张窄表，比如把用户基本信息和用户扩展信息分开。
三是水平拆分，也就是分库分表。把一张表的数据按规则分散到多个表或多个库，比如按用户 id 取模。好处是单表数据量下来了，代价是跨库 join、分布式事务、全局唯一 id 都变复杂了。

分库分表要谨慎，因为它引入的复杂度很高。能靠索引和缓存解决的，就不要分库分表。

七、常见问答
问：定位慢 SQL 的步骤是什么？答：先开慢查询日志找出执行超时的 SQL，再用 explain 看执行计划，重点看 type 是不是 all、key 是不是 NULL、rows 是不是很大，然后针对性加索引或改写 SQL。
问：limit 分页越翻越慢怎么解决？答：用游标法。不要写 limit 100000, 10，而是记住上一页最后一行的主键，下一页写成 where id 大于 上次的 id limit 10。这样每次只扫 10 行，速度恒定。

问：为什么 select 星号 不好？答：一是可能读了很多用不到的列，浪费 I/O 和网络；二是无法使用覆盖索引，必然回表；三是表结构变动时可能影响程序。
问：count 星号和 count 1、count 字段有什么区别？答：count 星号和 count 1 都统计所有行，包括 NULL 行，性能几乎一样；count 字段不统计该字段为 NULL 的行，所以结果可能更小。InnoDB 里三者都需要真实扫描，没有 MyISAM 那样的捷径。

问：什么时候该考虑分库分表？答：单表数据量到千万级、索引优化后依然慢、写入压力大、单机存储和连接数到瓶颈时。而且要评估业务能否接受跨库 join 和分布式事务的复杂度。
问：怎么判断一条 SQL 该不该加索引？答：看它出现在慢查询日志里的频率和扫描行数。高频而且 rows 很大的，优先加索引。另外注意写多读少的表要克制，因为索引会拖慢写入。
