========== 存储引擎：从零讲清楚 ==========

一、存储引擎是什么
存储引擎是 MySQL 里负责数据到底怎么存、怎么取的那一层。同样的 SQL，交给不同的存储引擎，底层的行为可能完全不同。
MySQL 的架构分两层：上层是 Server 层，负责解析 SQL、优化、权限校验、函数计算；下层是存储引擎层，负责真正读写数据。这种分层让 MySQL 可以换引擎而不改 SQL。

查看表用的引擎：show table status like '表名'; 或者 show create table 表名;
查看数据库支持哪些引擎：show engines;

二、InnoDB 和 MyISAM 的区别
InnoDB 在 MySQL 5.5 之后是默认引擎，它和 MyISAM 的主要区别有六条。
事务：InnoDB 支持事务，MyISAM 不支持。这是最根本的区别。
锁粒度：InnoDB 支持行级锁，MyISAM 只有表级锁。所以 InnoDB 的并发写入能力强得多。

外键：InnoDB 支持外键约束，MyISAM 不支持。
崩溃恢复：InnoDB 有 redo log，崩溃后能自动恢复；MyISAM 崩溃后容易数据损坏，需要修复。
索引结构：两者都用 B+ 树，但 MyISAM 的索引和数据是分开存的，索引的叶子节点存的是数据的地址，不是数据本身。所以 MyISAM 没有聚簇索引的概念。

行数统计：MyISAM 因为不支持事务，内部维护了一个精确的行数计数器，count(*) 能直接返回；InnoDB 必须真的去数一遍。
结论：新项目一律用 InnoDB。MyISAM 只在极少数读多写少、不需要事务的场景还有意义。

三、InnoDB 的内存结构
Buffer Pool（缓冲池）是 InnoDB 最重要的内存结构，用来缓存从磁盘读上来的数据页和索引页。
为什么要缓存？因为磁盘比内存慢上万倍。InnoDB 读数据时，先把整个页从磁盘加载到 Buffer Pool，之后的操作都在内存里做，只有需要时才写回磁盘。

Buffer Pool 的默认大小是 128MB，生产环境通常会调到物理内存的 50% 到 70%。
InnoDB 修改数据时，并不是立刻写回磁盘，而是先改 Buffer Pool 里的页，把它标记为脏页，然后由后台线程择机刷回磁盘。这个机制叫 WAL，也就是 Write-Ahead Logging，先写日志再写磁盘。

Log Buffer 是另一块内存，用来暂存 redo log，默认大小 16MB。

四、redo log 重做日志
redo log 记录的是某个数据页做了什么修改，是物理日志。
它的作用是保证持久性。事务提交时，InnoDB 会把这次修改写进 redo log 并刷盘，而不是等脏页刷回磁盘。因为 redo log 是顺序写而且体积小，比随机写数据页快得多。
如果数据库在脏页还没刷回磁盘时宕机，重启后可以拿 redo log 把丢失的修改重放一遍，数据就恢复了。

redo log 的大小是固定的，采用循环写，类似一个环。写满了之后，必须停下来把一部分脏页刷回磁盘腾出空间。
有个关键参数 innodb_flush_log_at_trx_commit 控制刷盘策略：等于 1（默认值）时每次提交都刷盘，最安全但最慢；等于 0 或 2 时性能好，但可能丢失最近一秒的数据。

五、undo log 回滚日志
undo log 记录的是数据的旧版本，作用是回滚和 MVCC。
事务执行 update 时，InnoDB 先把这一行的旧值写进 undo log，再修改当前行。如果事务回滚，就拿 undo log 把旧值恢复回去。
同时，undo log 里的旧版本被版本链串起来，供 MVCC 读取历史快照。所以 undo log 在事务提交后不能立刻删除，要等没有事务需要这些旧版本了才能清理。

六、binlog 归档日志
binlog 是 MySQL Server 层的日志，不属于任何存储引擎，记录的是做了什么操作，属于逻辑日志。比如把 id 等于 1 的这行的 name 改成张三。
它的主要用途有两个：主从复制，从库读主库的 binlog 重放；以及数据恢复，拿备份加 binlog 恢复到任意时间点。

binlog 有三种格式。statement 记录原始 SQL，省空间，但某些函数结果不确定；row 记录每一行数据的变化，精确但体积大；mixed 由 MySQL 自动选择。
MySQL 8.0 默认是 row 格式。实际生产也推荐 row，因为它更精确，不容易出现主从不一致。

七、redo log 和 binlog 的两阶段提交
redo log 和 binlog 都要写，而且要保证两者一致，否则主从数据会不一致。
InnoDB 用两阶段提交解决这个问题，步骤是：先写 redo log，标记为 prepare 状态；再写 binlog；最后把 redo log 标记为 commit 状态。

如果数据库在第二步之后、第三步之前宕机，重启后会先检查：如果 redo log 是 prepare 状态，就去 binlog 里找对应的事务。找到了就提交，找不到就回滚。这样保证两个日志要么都生效、要么都不生效。

八、常见问答
问：为什么 InnoDB 要用 B+ 树而不是哈希表？答：哈希表只支持等值查询，不支持范围查询和排序。B+ 树的叶子节点有序而且用链表串起来，既能等值查也能范围查，还能支持 order by。
问：redo log 和 binlog 的区别是什么？答：redo log 是 InnoDB 引擎层的物理日志，记录哪个页改了什么，循环写、空间固定；binlog 是 Server 层的逻辑日志，记录做了什么操作，追加写、会一直增长。

问：为什么建议用自增主键？答：InnoDB 的数据按主键组织成 B+ 树。自增主键是顺序增长的，新数据总是插到最右边，不会引起页分裂。UUID 这类随机主键插入位置随机，会导致频繁的页分裂和空间碎片。
问：Buffer Pool 是越大越好吗？答：不是。它太大会挤压操作系统和其他进程的内存，还要考虑刷脏页的抖动。一般建议设成物理内存的 50% 到 70%，剩下的留给系统。

问：innodb_flush_log_at_trx_commit 设成 1 会怎样？答：每次事务提交都把 redo log 刷到磁盘，最安全，不会丢数据，但每次都要等磁盘 I/O，性能最差。这是 MySQL 的默认值，也是金融类场景必须用的值。
问：MyISAM 的 count(*) 为什么快？答：MyISAM 不支持事务，没有并发修改产生的不确定性，所以它内部维护了一个精确的行数计数器，count(*) 直接返回这个数，不用扫表。InnoDB 因为要保证 MVCC 一致性，必须实际数一遍。
