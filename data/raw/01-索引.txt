========== 索引：从零讲清楚 ==========

一、索引是什么
索引是一种为了加快查询速度而额外建立的数据结构，它把某一列（或几列）的值单独拿出来，按顺序组织好，并记录每一行数据在哪。
索引最贴切的类比是书的目录。没有目录，你要找书里的某个知识点只能一页一页翻；有目录，先查目录定位页码，再直接翻到那一页，速度差出几十倍。
数据库里没有索引时，查询会做全表扫描：把整张表的每一行都读出来，逐行判断是否符合条件。数据量小的时候感觉不出来，一旦到了几十万行，全表扫描就是灾难。

索引的核心代价是空间和维护成本。索引本身要占磁盘空间；更麻烦的是，每当表里有新增、修改、删除，相关的索引都必须同步更新，这会拖慢写入速度。所以索引不是越多越好。

二、为什么 MySQL 用 B+ 树
先说结论：InnoDB 和 MyISAM 都用 B+ 树做索引，因为它在磁盘这个介质上综合表现最好。
要理解这个选择，先要知道磁盘有多慢。内存访问是纳秒级，磁盘访问是毫秒级，同一份数据从磁盘读比从内存读慢上万倍。
磁盘读写的最小单位不是字节，而是一个块（Linux 下通常是 4KB）。也就是说，就算你只要一个字节，磁盘也会把整块 4KB 读出来。所以设计索引结构的目标不是"比较次数少"，而是"磁盘 I/O 次数少"。

二叉查找树的问题是会退化成链表。如果按顺序插入 1、2、3、4、5，二叉树会长成一条斜线，查询退化成从头遍历，完全没有优化效果。
平衡二叉树（AVL）解决了退化问题，但每个节点只能存一个值、只能有两个子节点。一百万条数据，树高就有二十多层，每层都是一次磁盘 I/O，读一次数据要读二十多次磁盘——太慢了。

B 树的做法是让一个节点存多个值、有多个子节点。这样树的高度大幅降低，一百万条数据三到四层就能装下。B 树的每个节点既存索引值，也存完整的数据行。
B+ 树在 B 树基础上又做了两处改动：第一，只有叶子节点存数据，非叶子节点只存索引值；第二，所有叶子节点用一条链表从左到右串起来。
第一处改动的意义是：非叶子节点不存数据，同样大小的一个磁盘块就能装下更多的索引值，树的高度进一步降低。InnoDB 里一棵三层 B+ 树就能存两千多万行数据，查任意一行最多三次磁盘 I/O。

第二处改动的意义是：范围查询变得极快。比如查 id 大于 100 小于 200 的记录，先用 B+ 树定位到 100，然后顺着叶子节点的链表一直读到 200 就行。B 树做不到这一点，它必须在树里反复回溯。

三、索引的分类
按数据结构分，MySQL 里常见的有 B+ 树索引、哈希索引和全文索引。InnoDB 默认用的是 B+ 树索引，哈希索引只有 Memory 引擎支持，全文索引用于文本内容的模糊检索。
按物理存储方式分，分成聚簇索引和非聚簇索引（也叫二级索引）。这个区分是理解 InnoDB 的关键。

按逻辑功能分，有主键索引、唯一索引、普通索引、联合索引、前缀索引。
主键索引是建表时指定主键自动创建的，一张表只能有一个。它是 InnoDB 里的聚簇索引。
唯一索引要求被索引的列值不重复，可以有多个。主键本身就是一种特殊的唯一索引，区别是主键不能为 NULL，唯一索引允许一个 NULL。

普通索引没有任何约束，纯粹为了加速查询，可以建多个。
联合索引是把多个列合在一起建一个索引，比如（a, b, c）。联合索引比在每列单独建索引更省空间，也更适合"多条件一起查"的场景。
前缀索引是针对字符串类型的前几个字符建的索引，比如对一个很长的 URL 列只取前 20 个字符建索引。这样能大幅节省空间，代价是牺牲了一点精确度。

四、聚簇索引和二级索引
聚簇索引的意思是：索引和数据放在一起，索引的叶子节点直接就是完整的数据行。找到索引，就找到了数据。
InnoDB 的主键索引就是聚簇索引。所以 InnoDB 的表数据本身就是按主键顺序组织的一棵 B+ 树，这也解释了为什么 InnoDB 必须有主键。
如果建表时没有指定主键，InnoDB 会找一个不含 NULL 的唯一索引当主键；如果也没有，它会自动生成一个隐藏的 6 字节行 ID 作为主键。

二级索引的叶子节点存的不是完整数据行，而是索引列的值加上主键值。这是 InnoDB 的一个重要设计。
为什么二级索引要存主键值？因为这样能保证一致性。数据页发生页分裂、行记录移动位置时，二级索引里存的主键值不用改，只要改聚簇索引里的位置就行。

五、回表和覆盖索引
回表指的是：用二级索引查到了主键值，但查询需要的字段在二级索引里没有，只能再拿着主键去聚簇索引里查一次完整数据。这一来一回，就叫回表。
举例：表里有 id、name、age 三列，只在 name 上建了索引。执行 select age from user where name = '张三' 时，先在 name 索引里找到主键 id，再拿这个 id 去主键索引里取出整行，最后拿到 age。这中间的第二步就是回表。

覆盖索引指的是：查询需要的所有字段，在二级索引里都能拿到，不需要回表。执行计划里会出现 Using index。
接上面的例子，如果执行 select id from user where name = '张三'，因为二级索引的叶子节点里本来就存了主键值，不用回表，这就是覆盖索引。

覆盖索引是优化查询最常用的手段之一。实践中的做法是：把常用的查询字段一起放进联合索引，让查询变成覆盖索引。

六、联合索引和最左前缀原则
联合索引指的是把多个列拼在一起建一个索引，比如 index(a, b, c)。
建立联合索引时，数据库会先按 a 排序，a 相同时再按 b 排序，a、b 都相同时再按 c 排序。可以理解成先排序第一列，第一列相同的再排第二列，以此类推。
最左前缀原则说的是：使用联合索引时，必须从最左边那一列开始用，不能跳过。index(a, b, c) 能支持 a、a,b、a,b,c 这三种组合的查询，但支持不了 b 单独查、c 单独查、或者 b,c 的组合查。

为什么必须从最左边开始？因为数据是按 a 排好序的。如果直接给 b，b 在整个索引里并不是有序的——只有 a 相同的那些行里，b 才有序。全局范围内 b 是乱的，没法用二分查找。
范围查询会中断最左前缀。index(a, b, c) 执行 where a = 1 and b > 2 and c = 3 时，a 能用上索引，b 能用上（用于范围），但 c 用不上，因为 b 是范围查询，b 的值有多个，c 在这些值里不是全局有序的。

七、索引失效的场景
第一条：在索引列上用函数或运算。写成 where year(create_time) = 2026 或者 where id + 1 = 10，索引列被函数包住或者参与了运算，数据库无法用索引里的原始值去匹配，只能全表扫描。正确写法是改成范围查询，比如 where create_time >= '2026-01-01' and create_time < '2027-01-01'。

第二条：隐式类型转换。如果 id 是字符串类型，写成 where id = 123（数字），MySQL 会把字符串列转成数字再比较，索引失效。反过来，如果 id 是整数类型，写成 where id = '123'，MySQL 会把字符串转成数字，索引仍然有效。所以规则是：字符串列的查询一定要加引号。

第三条：like 以通配符开头。写成 like '%张三'，因为前面的字符不确定，没法用索引定位起点，只能逐行扫。改成 like '张三%' 就能用上索引。
第四条：用 or 连接的条件里有一边没有索引。写成 where a = 1 or b = 2，如果 a 有索引而 b 没有，整个查询会走全表扫描。因为 or 只要满足一个条件就行，b 那边必须逐行判断，a 那边的索引也就白建了。

第五条：对索引列做负向查询。不等于（!= 或 <>）、not in、not exists 这类否定条件，通常用不上索引。因为索引适合"快速定位一小片"，而否定条件往往要取大部分数据，还不如直接全表扫。
第六条：使用 is null 或 is not null。这一条要分情况。如果索引列允许为空，is null 通常能用索引；但 is not null 在数据大部分都不为空时，优化器会判断走索引不如全表扫。

第七条：联合索引不满足最左前缀。这一点在上一节讲过，是实际工作中最常见的失效原因。

八、用 EXPLAIN 查看索引使用情况
EXPLAIN 是 MySQL 提供的分析工具，用法是在 SQL 前面加两个字母：explain select ... 。它不会真正执行查询，只是告诉你优化器打算怎么执行。
type 字段是最重要的指标，表示访问类型，效率从高到低依次是：system、const、eq_ref、ref、range、index、all。

const 表示通过主键或唯一索引查到了唯一一行，是最快的。ref 表示用普通索引查到了多行。range 表示索引范围扫描。index 表示扫了整个索引树。all 表示全表扫描，这是要尽量避免的。
key 字段显示实际用到的索引名。如果这里是 NULL，说明没用上索引。possible_keys 显示理论上可用的索引，key 才是实际用的，两者不一致时通常意味着选错了索引。

rows 字段是预估要扫描的行数，这个数字越小越好。如果 rows 接近表的行数，基本就是全表扫描了。
Extra 字段里的信息很关键。出现 Using index 说明用了覆盖索引，是好消息。出现 Using where 说明服务器层还要过滤。出现 Using filesort 说明需要额外排序，通常意味着 order by 没有用上索引。出现 Using temporary 说明用了临时表，常见于 group by 没有用上索引。

九、索引设计原则
第一，只为经常被查询条件的列建索引。写多读少的表要谨慎建索引，因为每次写入都要维护索引。
第二，区分度高的列优先。区分度指的是"不同值的数量除以总行数"。性别列只有两三个值，区分度极低，建索引效果很差；订单号、手机号这种几乎不重复的列，区分度接近 1，建索引效果最好。

第三，尽量建联合索引而不是多个单列索引。联合索引能同时服务多种查询组合，而且占空间更少。
第四，把区分度高的列放在联合索引的左边。因为最左前缀原则决定了左侧列用得最多。
第五，尽量让常用查询走覆盖索引，把 select 要用到的列都放进联合索引里，避免回表。
第六，不要在索引列上做函数运算，也不要在索引列上用类型不一致的值比较。这是使用习惯问题，不是设计问题，但同样是索引失效的高频原因。

十、常见问答
问：索引是不是越多越好？答：不是。索引会占用磁盘空间，更重要的是每次增删改都要维护所有索引，直接拖慢写入。所以索引是"查询快"和"写入慢"之间的权衡。
问：为什么 InnoDB 必须有主键？答：因为 InnoDB 的数据本身就是按主键组织的一棵 B+ 树（聚簇索引）。没有主键，数据就没有组织依据。所以 InnoDB 会自动选一个唯一索引，或者生成一个隐藏行 ID 来充当主键。

问：为什么建议用自增主键而不是 UUID？答：自增主键是顺序递增的，新数据总是插到 B+ 树最右边，不会引起中间插入。UUID 是随机的，插入位置随机，会导致频繁的页分裂和数据移动，写入性能差很多，占用空间也大。
问：什么是回表？怎么避免？答：用二级索引查到了主键，但还要拿主键回到聚簇索引里取完整数据，这个动作叫回表。避免的办法是使用覆盖索引，把查询需要的字段都放进索引里。

问：什么是页分裂？答：B+ 树的叶子节点是一个个数据页。往已经满了的页里插入新数据时，这个页要拆成两个页，并把部分数据挪过去，这叫页分裂。页分裂会带来额外的性能开销和空间碎片，自增主键能有效避免它。
问：索引在磁盘上是怎么读取的？答：磁盘读写的最小单位是块，Linux 下通常 4KB。InnoDB 里一个数据页默认 16KB。每次读索引至少读一整页，所以索引结构的目标是让树尽量矮，减少读页的次数。

问：什么是索引下推？答：这是 MySQL 5.6 引入的优化。联合索引 (a, b) 执行 where a = 1 and b like '%x%' 时，本来要把 a = 1 的所有记录都回表，再由服务器层过滤 b。有了索引下推，可以在索引层就把 b 的条件过滤掉一部分，减少回表次数。

问：为什么范围查询后面的列用不上索引？答：因为联合索引的排序是"第一列有序，第一列相同时第二列才有序"。第一列做了范围查询后，符合条件的值有多个，后面的列在这些值之间并不是全局有序的，没法用二分查找。
